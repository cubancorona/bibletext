# Repository guidance

BibleText is a cross-platform Bible reader built from one Go module with
[Fyne](https://fyne.io/). The repository is public. Read [README.md](README.md)
for product usage, [ARCHITECTURE.md](ARCHITECTURE.md) for system design, and
[CONTRIBUTING.md](CONTRIBUTING.md) before preparing a change.

## Project layout

- The repository root is the shared `bibletext` library package. It is not a
  `main` package, so use `go run ./cmd/desktop` instead of `go run .`.
- `cmd/desktop` and `cmd/mobile` are the desktop and mobile entry points.
- `cmd/websitegen` builds the static web reader.
- Platform-specific behavior is selected with Go build tags. Host tooling may
  grey out files for other platforms; validate those files with the platform
  build commands below.

## Validate changes

Run the checks that cover the changed code, and run the full set before a
release or broad refactor:

```bash
go build ./...
go test ./...
go test -race ./...
go vet ./...
```

Format changed Go files with `gofmt -w <files>`. Use `git diff --check` to catch
whitespace errors and inspect `git status --short` before handing work off.

Launch the desktop application during UI work with:

```bash
go run ./cmd/desktop
```

## Platform builds

Mobile packages must use the repository scripts because they apply the required
Fyne patches and platform bridge code:

```bash
scripts/run-ios-sim.sh
scripts/run-ios-device.sh
scripts/release-ios.sh
scripts/build-android.sh
scripts/build-android.sh --release
```

Do not replace these with a bare mobile `fyne package` command. See
[patches/README.md](patches/README.md), [docs/ANDROID.md](docs/ANDROID.md), and
[docs/IPAD.md](docs/IPAD.md) for platform details.

The hand-written website pages live in `docs/`; the reader is generated by
`cmd/websitegen`. Build and verify the complete site with
`scripts/publish-site.sh --dry-run`. Publish only with
`scripts/publish-site.sh`, which preserves the required Pages files and reader
tree.

## Repository hygiene

- The product's identity — name, site origin, bundle ids, support mailbox,
  audio host — lives in `config/product.json` and derives from there. Never
  hardcode one of those values; `scripts/check-product-identity.py` holds the
  few tool-owned copies (FyneApp.toml, deep-link files) equal to it in CI.
- Keep changes scoped and preserve unrelated work already present in the tree.
- Never commit API keys, signing material, account identifiers, local
  environment files, or generated build artifacts.
- Use clearly synthetic fixtures in tests. Do not use real names, email
  addresses, family relationships, device identifiers, screenshots from a
  personal library, or local home-directory paths.
- Comments and documentation should explain behavior, constraints, and
  technical rationale without recounting a conversation or quoting a person.
- Do not add tool promotion, prompt transcripts, generated-by notices, or
  authorship trailers.
- Follow [docs/COMMIT_AND_CODE_PROTOCOL.md](docs/COMMIT_AND_CODE_PROTOCOL.md)
  for commit, comment, and documentation wording.
- Do not commit changes unless the task explicitly requests a commit.

Before handing off, report the commands run, their results, and any platform
validation that remains outstanding.
